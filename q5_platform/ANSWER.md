# 題 5｜低程式碼平台 vs 自己寫程式


## AI 協作
- 我先提出自己的想法，請 Claude 補充電商情境與判斷依據。
- 我說明參與過的專案。


## 1. 低程式碼平台 vs 自己寫程式

### 低程式碼平台
**初步想法：** 只需要產出個人化的內容、不需要在系統之間傳資料、檔案沒有機敏性。
**AI 建議：**
- **電商案例：客服新人的「退換貨規則問答助手」。** 把退換貨 SOP 文件放進知識庫，設定好 prompt，客服輸入問題，助手依文件回答。
- 判斷依據：
  - 只讀不寫：不碰訂單資料庫，不會改動任何資料。
  - 非機敏資料：SOP 是公司內部文件，沒有客人的個資。
  - 答錯風險低：客服會再次核對 SOP。
  - 規則常變動：由客服主管自己改文件和 prompt 最快。

### 自己寫程式
**初步想法：** 需要設定護欄、和其他系統交互。
**AI 建議：**
- **電商案例：可以查詢與取消訂單的訂單助理。**
- 判斷依據：
  - 權限控管：必須檢查這張訂單是不是這位登入者的。
  - 資料庫操作：SQL 要用參數寫法避免注入，金鑰要由環境變數或 Secret 管理。
  - 限制模型呼叫哪些工具、呼叫次數，並處理逾時與重試。
  - 需要自動化測試、查核正確性，證明「查不到別人的訂單」「已出貨的訂單不能取消」。
  - 涉及個資、要接內部系統。

### 折衷做法
- 先用平台快速驗證需求，確定有價值後，把核心邏輯搬到自己的程式。
- 平台負責對話流程，需要碰資料或執行動作時，呼叫自己寫並測試過的 API。


## 2. AI 專案

### 專案說明
- **公司專案： AI Agent平台導入與應用_徵信報告助手**
- **個人專案：財富管理 AI 助手**

| 項目 | 徵信報告助手 | 財富管理 AI 助手 | 
|---|---|---|
| 親手寫的程式 | 無 | 產品設計說明文件、套件管理 | 
| 平台設定 | 使用者、知識庫、Prompt、工具調用 | 無 |
| 其他工程師廠商 | 無 | 無 | 
| AI 工具產出我修改 | Gemini 討論業務流程與 prompt 撰寫 | Claude 針對產品設計說明文件產程式碼，我修正資料樣態、抽出環境變數、調整程式碼 | 

### 問題排除
- **問題**：財富管理 AI 助手，評估指標的分數偏低
- **現象**：評估程式由 Claude 撰寫，用 RAGAS Faithfulness 評估 LLM 生成的自由文字，商品理由平均只有 0.53，低於客戶洞察的 0.89。
- **原因**：
  - 對照商品理由的 prompt 與評估用的 context，prompt 要求模型說明「商品風險與客戶風險的關係」，理由常寫「與客戶的高風險承受度相符」，但評估時給裁判的 context 只有商品資料，沒有「客戶風險等級」，所以裁判判為無依據。
  - 我追問 RAGAS 的運作方式，Claude 讀原始碼發現一直沒有傳入參數 user_input。
- **修正**：
  - 商品理由的 context 加入「客戶風險等級」。
  - user_input 改成必填，說明這段內容在回答的問題。
  - 商品理由 0.53 → 0.69，但模型的 temperature 無法控制，所以不能把差異全部歸功於這次修正。
- **預防**：評估自由文字前，先確認裁判看到的 context 涵蓋文字可能提到的資訊。
